# CI и выпуски

[Процесс выпуска](../../.github/workflows/windows-installer.yml) запускается
для веток, pull request, тегов версий и вручную. Текущий путь сборки задаёт
десять [профилей](profiles/README.md), по умолчанию `main`; все используют схему03.
Опубликованные пакеты и результаты проверки устройства записываются отдельно
в [статусе](STATUS.md).

## Прошивка и установщики

Задание Ubuntu 24.04 проверяет синтаксис Python и shell, workflow закреплённым
actionlint, неопределённые имена Python закреплённым Ruff и автономные тесты.
SDCC 4.6.0, LUFA и окружение QMK используют закреплённые зависимости; actions
закреплены полным commit hash. Клавиатура, приватный OEM ROM и сессии устройства
в CI не передаются.

После общих проверок десять заданий матрицы запускают сборщик с `--profile <имя>`. Каждое сохраняет полные каталоги итоговой и начальной сборок. Отдельное задание упаковки требует успеха всех десяти, восстанавливает каталоги по тем же путям checkout и повторяет проверки допуска точных образов. Без `--profile` локально собираются все десять.

Все профили собирает `tools/build_ci_profiles.py`. Для каждого создаются свежая
начальная сборка и контекст исходников/IRQ, затем сборка pass30. Границы стека
основной программы, запуска и IRQ итогового образа проверяются до полной
основной и профильной регрессии. Начальные доказательства нельзя менять.
Неизвестные пути, отсутствие контекста, переполнение, ошибки и пропуск обязательных
проверок останавливают процесс. Модели потери питания не доказывают физическую
сохранность данных.

Локальная сборка всех десяти (workflow добавляет один `--profile` на задание матрицы):

```sh
python tools/build_ci_profiles.py \
  --builds-root qmk-8051-ak820/.build/ci-profiles \
  --bootstrap-root qmk-8051-ak820/.build/ci-profile-bootstrap \
  --toolchain toolchains/sdcc-4.6.0 \
  --qmk-bin qmk-8051-ak820/.venv/bin/qmk \
  --python qmk-8051-ak820/.venv/bin/python \
  --report qmk-8051-ak820/.build/ci-profile-builds.json
```

Каталоги вывода должны быть новыми. Команда выполняется из корня после установки
закреплённых зависимостей и окружения QMK по [инструкции сборки](BUILD.md).
Нельзя одновременно запускать сборки в одном дереве исходников.

После квалификации `tools/build_ci_release.py --all-profiles` проверяет политику
каждого профиля из `ci/profiles`, независимые ревью, квитанции упаковки и
`tools/installer/settings-catalog.json`. Полные пакеты создаются в
`dist/ci-firmware/profiles/<profile>`. Отсутствие или устаревание входов допуска
останавливает процесс. Одного связанного образа недостаточно.

Задание упаковки также формирует каталог возможностей по этим точным CI-сборкам. Публикация использует его и измеренную матрицу: зависящие от пути хеши MAP и отчётов относятся к допущенным файлам CI, а не заменяются хешами локальных сборок.

Задания Windows и Linux скачивают пакеты того же запуска, проверяют commit
исходников и переносят их в `releases/beta2/<profile>`. Каждому доступному профилю
нужны собственные совпадающие манифест и допуск. Упаковка сверяет входы внутри
GUI и CLI. Windows проверяет нативный запуск; Linux использует Ubuntu 22.04
x86_64/glibc 2.35 и Xvfb. Справка CLI, автономная проверка и запуск Tk не открывают
USB и не доказывают поведение с устройством.

## Время проверки

Тяжёлая проверка цепочки оптимизаций pass30 выполняется один раз для неизменной
сборки в рамках одной проверки. При сборке выпуска
`tools/ci_parallel_assembly.py --validation-workers 4` распределяет первые
проверки по четырём процессам. Результаты передаются основному процессу через
память; обычный сборщик перед использованием заново сверяет все входы.
С `--validation-workers 1` эти же проверки идут последовательно. Обычная
команда `tools/build_ci_release.py` продолжает работать. Перед повторным
использованием результата
заново считаются хеши всех входов: исходников и проверяющего кода, промежуточных
файлов и состава каталогов, компилятора, заголовков и библиотек, зависимостей
раскладки, доказательств начальной сборки и окружения процесса. Проверяется
содержимое файлов, а не время изменения. Изменённые или неподдерживаемые входы
проходят полную проверку заново. Неуспешный результат не сохраняется.

Кеш существует только в памяти процессов текущего задания. Он не загружается
с диска и не переносится между запусками CI. Ошибка любого процесса останавливает
сборку выпуска. Каждое новое задание выполняет первую полную
проверку самостоятельно. Остальные проверки образа, исходников, памяти, стека,
IRQ, журналов тестов и допуска к выпуску выполняются при каждом обращении.
Новые журналы тестов не меняют входы цепочки оптимизаций. Для каждого набора
тестов выводятся общее время и время самого теста. Готовые ZIP и gzip-архивы
отправляются без повторного сжатия.

## Каталоги и доказательства

Матрица исходников может содержать десять неизмеренных строк. Каталог возможностей
остаётся пустым до импорта проверенных точных записей. Нельзя переносить прежние
идентификаторы в текущие строки. Каталог не разрешает запись и не доказывает
работу устройства; см. [каталог разработки](DEVELOPMENT-CATALOG.md).

Отдельный [процесс кандидатов](../../.github/workflows/firmware-catalog.yml) и
`tools/build_profile_catalog.py` экспортируют кандидатов для разработки, не
допуск к выпуску. Свежему пути текущего профиля обязателен контекст исходников и
IRQ. Прежний процесс девяти профилей не подтверждает новые составы. Полные журналы
и промежуточные доказательства сохраняются, включая частичные результаты ошибок.

Политика профиля закрепляет точные IHX, символы MAP, входы сборки и файлы
установщика. Квитанция упаковки описывает прежние локальные проверки с приватными
reference; CI не повторяет зависящую от OEM упаковку в облаке. Машинное повторение
и допуск пакета не заменяют независимое ревью и не разрешают запись в клавиатуру.
Изменение исходников или кода установщика требует новых доказательств.

## Публикация и локальные проверки

Публикация возможна только по допустимому SemVer-тегу проверенного commit в
`main` после обязательных заданий. Ветки, pull request и ручные проверки создают
артефакты без публикации. Право записи получает только задание публикации.
Локальные тесты не создают тегов и выпусков. Самостоятельные пакеты Windows/Linux,
SHA256 и инструкции EN/RU остаются обязательными. Фактическая публикация
записывается отдельно в статусе.

Имена обязательных заданий:

- `Linux syntax and shared host checks`.
- `Qualify firmware (<profile>)` — все десять профилей.
- `Revalidate and assemble all ten profiles`.
- `Native Windows package build and smoke`.
- `Native Linux x86_64 package build and smoke`.

Локальные проверки синтаксиса и документов: `python tools/ci_checks.py` и
`python tools/check_docs.py`. Квалификация уже собранного текущего образа:

```sh
python tools/configure_firmware.py qualify \
  --build-dir qmk-8051-ak820/.build/local-1 \
  --toolchain toolchains/sdcc-4.6.0
```

До доказательств runtime и регрессии повторно проверяются сохранённый контекст
и вся цепочка преобразований. Локальный результат не подтверждает успешный
запуск GitHub, публикацию или аппаратное поведение.
