# CI и выпуски

[Workflow](../../.github/workflows/windows-installer.yml) запускается при каждом
push ветки, pull request и теге `v*`. Его также можно запустить на странице
Actions. Для проверок и сборок не нужны клавиатура, OEM-копия или секрет
репозитория.

Workflow закрепляет actions с Node.js 24 по полному хешу коммита: checkout 7.0.1, setup-python 7.1.0, upload-artifact 7.0.2 и download-artifact 8.0.2.

## Проверки и результаты сборки

Workflow собирает профиль `full` через конфигуратор и запускает его проверки.
В опубликованном выпуске `v0.6.0-alpha.3` используется этот профиль. CI
воспроизвёл одобренный образ и собрал пакеты выпуска. Остальные семь профилей
предназначены для разработки. См. [профили сборки](BUILD-PROFILES.md) и
[статус](STATUS.md).

Задача сборки прошивки на Ubuntu 24.04 проверяет синтаксис отслеживаемых
файлов Python и shell, проверяет workflow через actionlint с закреплённой контрольной суммой,
ищет неопределённые имена в проектном Python через закреплённый Ruff и
запускает все юнит-тесты host-инструментов. Затем скачивает закреплённые архивы SDCC 4.6.0 и LUFA,
сверяет их хеши, собирает профиль `full` через конфигуратор, запускает основные
и дополнительные host C и CPU-проверки полного профиля и записывает анализ
стека точного образа.
Отдельные тесты хранилища моделируют прерывание записи журнала и макросов.
Эти проверки не доказывают работу физического USB, подсветки и флеш-памяти.

Для коммита, допущенного к выпуску, после успешных тестов Linux создаёт
новый публичный комплект прошивки из
IHX, MAP, MEM и отчёта этой сборки. Задача Windows скачивает комплект,
проверяет его коммит и заменяет прежние входы выпуска в checkout перед
сборкой обоих установщиков. Она запускает справку CLI и офлайн-проверку,
создаёт и закрывает интерфейс Tk. Это проверка запуска, а не проверка видимых
диалогов и интерактивной работы.

Задача сборки Linux-пакета работает на Ubuntu 22.04 для x86_64 (glibc 2.35).
Она создаёт `AK820-Linux-x86_64.tar.gz` и файл SHA256. Сборщик проверяет импорт
hidraw в собранном приложении, справку CLI, офлайн-проверку и запуск Tk под
Xvfb. Эти проверки не открывают USB и не проверяют работу клавиатуры.

На коммитах, прошедших правила допуска, push ветки создаёт артефакты без
публикации релиза. Публикация выполняется только по прошедшему проверки тегу версии. Результаты
допущенной сборки выпуска:

- Отдельный публичный комплект прошивки с SHA256 и результатами сборки.
- Полный переносимый Windows ZIP с SHA256 и отчётами проверки запуска.
- Переносимый Linux tar.gz с SHA256.
- Журналы host/CPU-проверок прошивки.

IHX приложения не является полным ROM для прошивки. Установщик создаёт образ
обновления из свежей резервной копии и локальных данных восстановления OEM.
OEM ROM, приватные сессии и снимки устройства не попадают ни в workflow,
ни в его артефакты. Установщики Windows и Linux содержат новую сборку прошивки,
а не прежние отслеживаемые файлы `releases/rc6/firmware`. Перед публикацией
папки GUI и CLI в обоих пакетах сверяются с комплектом прошивки из того же
запуска.

## Ревью и повторяемая сборка

В `ci/release-policy.json` записаны хеш прошедшего независимое ревью IHX,
хеш всех разобранных символов MAP, host-код и исходные входы сборки и тестов.
`ci/program-review.md` связывает результат настоящего независимого ревью
с этим правилом. В `ci/packing-receipt.json` сохранены результаты прежней
локальной проверки упаковки этой точной программы с приватными OEM-данными.

CI должен воспроизвести проверенную программу и адреса символов, использовать
закреплённый инструментарий и пройти все обязательные наборы без пропусков.
Проверенные входы сверяются с текущим Git-коммитом. Затем создаются машинный
отчёт сборки и одобрение точного комплекта. Этот отчёт подтверждает повторение
проверенной сборки, а не новое независимое ревью или разрешение записи
в клавиатуру.

После изменения прошивки или проверенных host-входов нужно обновить правило
и результат независимого ревью. При изменении входов упаковки повторяются
затронутые локальные проверки. В Git сохраняются доказательства и хеши;
новые собранные файлы прошивки не нужно вручную помещать в каталог выпуска
или коммитить ради CI. Устаревшее правило останавливает упаковку. CI использует
проверенный результат упаковки точной программы и не утверждает, что облачный
запуск повторяет упаковку с OEM-данными.

## Выпуск релиза

Обычный автоматический путь: создать новый SemVer-тег на проверенном коммите
`main`, например `v0.6.0`. Тег запускает публикацию после успешных трёх задач
сборки.
Тег на коммите вне `main` не может выпустить релиз. `v0.6.0-rc.1` создаёт
предварительный выпуск; метаданные версии вроде `+build.1` тоже принимаются.
Ручной запуск workflow только проверяет и собирает. Обычный push ветки и pull
request не публикуют релиз.

Релиз `v0.6.0-alpha.3` опубликован через GitHub release API на основе трёх
успешных нативных задач для того же коммита, до отмены запущенного тегом
дублирующего workflow. В отменённом запуске не было ошибки теста, но он не
завершился успешно как запуск по тегу. Этот разовый способ публикации не меняет
обычный автоматический путь по тегу.

В релиз входят публичный комплект прошивки, Windows ZIP и Linux tar.gz; для
каждого файла прилагается SHA256.
Право `contents: write` получает только задача публикации; проверки и сборки
работают с правом чтения. Локальные тесты не создают тег и релиз. Локальные
команды сборки и упаковки находятся в [Сборке](BUILD.md).

Правила защиты ветки задаются отдельно в настройках GitHub. Если защита
включена, укажите три задачи как обязательные проверки:

- `Linux syntax, host, CPU, and pinned firmware build`.
- `Native Windows package build and smoke`.
- `Native Linux x86_64 package build and smoke`.

## Локальные проверки

Из корня репозитория:

```sh
python3 tools/ci_checks.py
python3 tools/check_docs.py
python3 -B tools/test_keyboard.py --host \
  --build-dir qmk-8051-ak820/.build/local-1 --require-toolchain \
  --toolchain toolchains/sdcc-4.6.0 --iap-fault-profile guarded-erase
```

Для последней команды нужна готовая сборка закреплённым инструментарием.
Она не открывает USB. Workflow также запускает тесты отдельных инструментов
и хранилища; точные команды находятся в его файле. Локальный PASS не означает,
что задачи GitHub уже выполнялись. Результаты запусков описываются в
[Статусе](STATUS.md).
