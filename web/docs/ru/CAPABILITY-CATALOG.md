# Каталог возможностей сборок

`tools/build_capability_catalog.py` создаёт локальный каталог полностью
проверенных конфигурируемых сборок для разработки. Это часть этапа 2 PLAN и
AKW-012/034. Каталог выпущенных образов, отзыв версий, определение установленного
образа и разрешённые переходы настроек пока не реализованы.

```sh
python tools/build_capability_catalog.py \
  --build-dir qmk-8051-ak820/.build/example \
  --toolchain /path/to/pinned-toolchain --output /tmp/capabilities.json
```

Для нескольких образов параметр `--build-dir` повторяется. Каталоги сборок
должны находиться внутри дерева QMK. Сначала требуется полная проверка через
конфигурируемый сборщик. Генератор читает только локальные файлы и не обращается
к устройству. Отсутствующие, изменённые, устаревшие или неполные данные
останавливают генерацию. Готовый файл заменяется после проверки всех сборок.

Проверка повторно сверяет исходные данные компилятора, профиль, символы функций
и байты команд в связанном образе, хеши IHX/MAP/MEM, запуск и размещение памяти.
Сводка безопасности стека заново составляется из отчётов основной программы,
запуска и прерываний с проверкой текущих анализаторов. Отчёт конфигурации должен
совпасть с результатом. Обязательные основные и дополнительные тесты должны
пройти для этого образа; проверяются журналы и текущие исходники дополнительных
тестов. Основные журналы должны находиться внутри каталога сборки; сверяются
их SHA256, прочитанные числа тестов и общие суммы. Это данные сборки и моделей на компьютере, а не проверка устройства
или независимое разрешение выпуска.

Формат JSON — `ak820-development-capability-catalog-1`. Для образа записаны
модель `ajazz/ak820`, схема настроек, функции, постоянные ограничения из связанных
с компиляцией исходников, интервалы профиля, ресурсы и хеши файлов доказательств.
Идентификатор CODE использует `sha256-code-windows-zero-v1`. SHA256 охватывает
префикс ASCII `ak820-code-windows-zero-v1`, нулевой байт, затем для каждого
диапазона его начало и конец без включения как четырёхбайтовые числа big-endian
и все байты диапазона. Диапазоны: `[0x28a0,0x3000)` и `[0x3027,0xc700)`.
Адреса, отсутствующие в IHX, заполняются нулями, как при очистке области
приложения упаковщиком перед наложением CODE. JSON содержит диапазоны, байт
заполнения и число проверяемых байтов. Ненулевой байт в пропуске меняет
идентификатор. Явный нулевой байт и нулевое заполнение дают одинаковый результат.
Повторяющиеся идентификаторы отклоняются. Порядок и JSON детерминированы;
каталог не содержит времени генерации и локальных путей сборок.

Этот хеш определяет два диапазона связанного CODE. Он не охватывает область
запуска и прерываний, создаваемую упаковщиком, настройки, защищённые области
или весь установленный образ. Будущая проверка устройства должна читать все
байты обоих диапазонов, включая пропуски, и отдельно проверять остальные
области по связанным IHX и правилам упаковщика. Чтения только занятых адресов
IHX недостаточно. Проверка устройства здесь не реализована. Закрытые
эталонные байты OEM в каталог не попадают.

Хеши отчётов подтверждают локальную согласованность; они не являются подписью
или аутентификацией. Отчёты и журналы из одного источника не доказывают
независимую проверку.
Поддержка в исходниках, проверенная сборка для разработки и установленная
прошивка — отдельные состояния. Название профиля не определяет установленный
образ. Перед показом возможностей будущему клиенту требуется полная проверка
установленного образа. Частичное чтение и неизвестный образ ничего не разрешают.
В каталоге разработки поля `release_approved` и `hardware_validated` равны
false; запись настроек и прошивка не разрешаются, список совместимых переходов
пуст. Каталог выпуска может отдельно одобрить точные образы для тестовой beta-
прошивки. Это не подтверждает физическую проверку и не разрешает запись
настроек. Действуют проверки установщика и отдельное свежее подтверждение для
каждой операции.
