# SDCC 4.6.0 compatibility probe preparation

Date: 2026-10-23

## Purpose and boundary

Record an isolated compile of the AK820 USB translation unit that triggered the SDCC 4.5 compiler failure, then compare an authorized private SDCC 4.6.0 whole-project artifact with the matched SDCC 4.4.0 build. This is compiler and linked-image evidence. It does not test the keyboard.

The official Linux amd64 archive is staged under `qmk-8051-ak820/.build/rc6-sdcc46-probe-20261023/sdcc-4.6.0/`. No source or production toolchain was changed. The pinned SDCC 4.4.0 remains the production compiler. The archive is from the official SourceForge SDCC listing: https://sourceforge.net/projects/sdcc/files/sdcc-linux-amd64/4.6.0/ . The requested `downloads.sourceforge.net` URL returned an HTML challenge in this environment; using the official pilotfiber mirror URL redirected to a signed SourceForge mirror download.

## Candidate translation unit and saved flags

The prior failure description names `tmk_core/protocol/ch555/usb_ak820.c`, in `validateOpType` / `OP_USES` inside SDCC 4.5's optimizer (`SDCCopt.c:2823`). ## Isolated translation-unit compile

The root authorized one compile after the canonical combined build finished. It used the current `rc6-optimization-batch-20261023` build output, not the older `rc6-final-3` flags. The build report identifies build ID `532482`, SDCC 4.4.0 #14620, and 39,144 CODE bytes. The source hash matched the completed build manifest before compilation.

The command and input hashes are preserved in `qmk-8051-ak820/.build/rc6-sdcc46-probe-20261023/single-tu/command.json`. It invokes the isolated SDCC 4.6.0 binary with the saved `cflags.txt`, adds `-c -o <probe>/single-tu/usb_ak820.rel`, and compiles only `tmk_core/protocol/ch555/usb_ak820.c`. Working directory was the QMK source root. Inputs fingerprinted in `command.json` include the translation unit, saved flags, completed build report, generated headers, forced config headers, and compiler, preprocessor, and assembler executables.

Result: exit code `0`; `usb_ak820.rel` was emitted (54,106 bytes, SHA-256 `8760d2e98b1a554505970225cd06d3ddc38e22a9c0b68a86d9fff04eec304b13`). The compiler emitted warning 291 at `quantum/keycodes.h:89`: “enumeration constant outside the range of int requires ISO C23 or later”. Full stdout and stderr are in `single-tu/stdout.txt` and `single-tu/stderr.txt`; the command, exit code, assembly, listing, symbol file and REL are all kept under the probe directory.

This passed compile established compatibility for that source and flag set. The separate full-project experiment below now records whole-project compile and link evidence. Neither step proves physical keyboard behavior. No source was changed.

## Full-project experiment

The production builder's pinned-version guard remains unchanged. A private
copy, `build_ak820_experimental.py`, changed only the expected compiler version
and the source-root expression needed for its location. Its SHA256 is
`4094ceba4c883b70355fb6fefa8a219cb18a0847bfbcb623c1e5833feaf276db`;
`prepare_builder.py` records the substitutions. Firmware sources and the
production builder were not changed.

The completed private build is in
`qmk-8051-ak820/.build/rc6-sdcc46-full-experiment-20261023/`. It exited 0 and
linked an Intel HEX image with SHA256
`f1c4347e60ca5f7ea6c557debe60272259f4ddf9acfac9897fa992210bf7ef2e`.
Its linker-reported CODE is 38,100 bytes: 36,292 in the main window and 1,808
in the low window. Against the completed SDCC 4.4.0 control
`.build/rc6-optimization-batch-20261023/` (39,144 total; 37,285 main; 1,859
low), this is 1,044 fewer CODE bytes (993 main, 51 low). XRAM is 2,067 bytes
in both builds; reported stack is 157 versus 152 bytes. These are linked-artifact
measurements, not proof of firmware behavior or a reason by themselves to
adopt a new compiler.

The experiment and control both use build ID 532482, 465 manifest entries and
130 successful compile commands. The 443 project-source entries match after
normalizing build-directory paths. Their 117 CFLAGS entries match after the
same normalization; extra flags and the audited callee-saves list also match.
The remaining manifest differences are the isolated compiler/toolchain files
(16 of 22 toolchain entries differ). The private builder transformation was
verified to contain exactly the expected version and root-path substitutions.

The `.mem` ROM total and sum of map CODE areas are 38,105 bytes, five more
than the 38,100 occupied IHX bytes. The map includes a five-byte HOME span at
`0x302a–0x302e`; those addresses are absent from the IHX records. Thus these
figures use different accounting, and the five-byte gap is not extra emitted
HEX data.

The dead-code reports each contain 576 functions and the same 27 root symbols.
SDCC 4.6 retains 387 versus 399 in 4.4; it outlines 29 functions at 182 sites
versus 32 at 221 sites. The 12 functions removed only in the 4.6 report are
empty callback/trampoline stubs in the generated assembly for this build; the
mouse registration stub is disabled by the saved configuration. No root
symbol was lost in the report. This is evidence for compiler-side elision in
this exact configuration, not proof that arbitrary weak-callback overrides
are safe in other configurations.

The build log contains 137 warning occurrences at 89 unique source sites;
31 repeats are one enum-range warning at `quantum/keycodes.h:89`, and 20 are
two read-only-code warnings in `gpio.c` and `_pin_defs.h`. Compared with the
4.4 log, there are 11 new unique warning sites and no baseline-only sites.
There are also five SDCC “Internal issue” diagnostics concerning inline
definitions after extern declarations (`clear_keys`, `add_key`, `del_key`,
`timer_read_fast`, and `timer_elapsed_fast`). These are outside the warning
count and remain compiler diagnostics requiring caution; the link succeeded.
Root separately reports that all 465 source-manifest checks, 76 additional
manifest checks, and 19 offline regression suites passed. The earlier value
`60351` was a process session identifier, not a test count. No test-count claim
is inferred from it. Neither build nor host checks demonstrate physical
keyboard behavior. No USB activity or flashing occurred.

## Evidence interpretation

- Source behavior: unchanged during this experiment.
- Compiler compatibility: the USB translation unit compiled, and the complete
  configured project compiled and linked with SDCC 4.6.0 in an isolated build.
- Linked benefit: measured as 1,044 fewer linker-reported CODE bytes against
  the same-configuration SDCC 4.4.0 control; XRAM is unchanged and stack
  increased by five bytes.
- Host validation: root reports all 465 source-manifest and 76 additional
  manifest checks passed. CPU regression state and counts are not inferred from
  process session identifiers in this audit.
- Installed firmware and device behavior: not tested. No image was flashed.
- Adoption: not established by this experiment; compiler diagnostics and
  device-level validation remain separate considerations.

## Separate compiler and linked-path checks

The narrow Boolean-pointer compiler gate has a known failing case under both
SDCC 4.4.0 and 4.6.0. Results are preserved at
`qmk-8051-ak820/.build/compiler-gate44-v3-20261023/results.json` and
`qmk-8051-ak820/.build/compiler-gate46-v3-20261023/results.json`. In each,
both input values fail only the `near` case (`near_store(box_t __data *)`,
`tests/ak820_compiler/fixture.c:16`), whose body stores a Boolean comparison
through a typed `__data` pointer. The other seven cases pass for both values.
Because 4.4.0 fails identically, this fixture identifies an existing compiler
limitation, not a new 4.6-only regression. The broader applicability of this
fixture to production code remains under review.

The linked-image source-record check is separate. Its 4.4 and 4.6 results are
in `compiler-linked44-v3-20261023/results.json` and
`compiler-linked46-v3-20261023/results.json`; all eight named matrix press,
matrix release, record press/release, and encoder CW/CCW true/false paths
passed for the tested images. These are executed CPU-model paths through the
existing linked images, not proof about every possible record layout,
compiler optimization path, physical key/encoder, USB timing, or installed
firmware.
